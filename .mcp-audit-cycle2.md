# MCP audit — cycle 2 (gpt-sol)

## Verdict on the 8 cycle-1 fixes

- **CONFIRMED — cycle-1 F1 (streaming stdout UTF-8).** `src/mcp/client.ts:1061–1092` uses one persistent `StringDecoder`; valid split CJK/emoji sequences reassemble before JSON parsing and completed-frame byte measurement. Its private carry is at most three bytes; it is not reused across transports, and EOF is terminal rather than a decoder-reset/reconnection path. The split-character regression passes. Partial-frame measurement can lag raw input by those at-most-three carried bytes, but a completed oversized valid frame is rejected; this is not an unbounded decoder leak.
- **INCOMPLETE — cycle-1 F2 (unsent-frame release).** Ordinary `settle()` correctly removes an unsent frame (`1432–1449`), and the queued-tool timeout regression passes; write-started reservations survive settlement, and `removeUnsent`'s released guard prevents abort's second removal from double-decrementing. However, probe settlement bypasses that helper: `settleProbeTimeout()` (`1456–1463`) deletes the request without removing its queued frame. Reproduction: before `start()`, receive a server request whose mandatory reply occupies a stalled active write, then start and let the queued probe expire. Stats after timeout are `undrained: 482, queued: 2, pending: 1`; recovering writes sends the expired `server/discover`, then `initialize`. This is the same original unsent-settlement defect on the probe branch, not a new finding. **Suggested completion:** share an exactly-once pending cleanup/frame-release helper across ordinary and probe settlement, and test a probe queued behind mandatory control traffic.
- **INCOMPLETE — cycle-1 F3 (version negotiation and discovery validation).** Intersection selection, unsupported-only rejection, retry agreement (`419–477`), and the documented `-32022` retry/legacy fallback work; the existing regressions pass. But `probeResult` still accepts *any* string `resultType` and any array `supportedVersions` (`541–552`): both `{resultType:"garbage", supportedVersions:["2026-07-28"]}` and `{resultType:"discovery", supportedVersions:["2026-07-28",123]}` reproducibly reach modern ready. Legacy validation (`620–628`) accepts any regex-shaped date except the one modern constant; even `2099-99-99` reaches legacy ready. This contradicts §6's unknown-version startup-failure requirement and leaves the original discovery-validation finding unresolved. **Suggested completion:** validate the discovery discriminant and all version entries, define an explicit supported legacy-version policy (not merely a date-shaped-string test), and reject invalid/unknown legacy versions with the observed and supported values. Add these negative cases plus a successful retry that advertises a different version from the selected one.
- **CONFIRMED — cycle-1 F4 (per-tool annotations).** `client.ts:684–695` preserves each entry's annotations across pages; `adapter.ts:157–158` prefers defined per-tool annotations, otherwise retains the import-level fallback. Registry-to-adapter regression passes. Manually constructed tools still receive fallback annotations; the separate fixed-name `mcp_resource` constructor is unaffected and remains read-only by the documented classification convention.
- **INCOMPLETE — cycle-1 F5 (terminal-failure full cleanup).** Failures after hook installation correctly kill first, call the hook once, share the handle's teardown promise with `teardownAll`, and leave unconfirmed cleanup retryable; clean `close()` does not fire the hook. The regression passes. There is nevertheless a startup-completion gap: `runStartup()` returns the tool list even when the client failed after its last list response (`client.ts:481–488`), and the registry installs the hook only after awaiting startup and importing tools (`registry.ts:187–195,242–256`). Reproduction: send the final valid `tools/list` response followed by `not-json\n` in the **same stdout chunk**. `startMcpServers` returns a `ready` handle with an actually failed client, exports its ghost tool plus `mcp_resource`, and records `kills:1, closes:0, disposes:0`; no hook was installed when failure occurred. **Suggested completion:** reject startup if closed/failed before publishing success, install cleanup ownership before asynchronous startup can fail (or immediately reconcile failure when installing the hook), and test coalesced final-response-plus-fatal input. This is an uncovered branch of the original full-cleanup finding, not counted again below.
- **CONFIRMED — cycle-1 F6 (admission-rejection abort listener).** `client.ts:775–791` routes tool admission rejection through `settle`, detaching the listener and timer exactly once. Its frame is null because rejection precedes reservation; it cannot release the unrelated active write. The counting-signal regression passes.
- **INCOMPLETE — cycle-1 F7 (64 KiB stderr tail).** Complete valid UTF-8 chunks are trimmed at the leading boundary and the CJK regression passes, including the exact-cap comparison. However, `client.ts:1102–1113` decodes an incomplete *trailing* sequence independently for every diagnostic view: 65,535 ASCII bytes plus byte `0xe6` retain 65,536 raw bytes but expose **65,538 UTF-8 bytes** after replacement decoding. Invalid byte runs can inflate the view further. Also, the retained `subarray` owns the **entire concatenated backing allocation**, not just its 64 KiB logical slice: an inline 8 MiB stderr-chunk reproduction left `stderrTail.length === 65536` but `stderrTail.buffer.byteLength === 8454144`. Thus neither the exposed diagnostic-byte bound nor retained-memory bound is strict. **Suggested completion:** keep incomplete trailing UTF-8 bytes separately from the decoded diagnostic view, byte-bound the exposed replacement-decoded text too, and copy the retained tail into a bounded allocation rather than retaining a slice of the large concat. Test split trailing sequences, invalid UTF-8, exact cap, and backing-allocation size. These are remaining boundary/resource aspects of the original stderr-ring finding, not new findings below.
- **CONFIRMED — cycle-1 F8 (tools/list entry validation).** `client.ts:668–682` validates object shape before dereferencing `name`; null/scalar entries use `McpStartupError` at startup and `McpCallError` when ready. The null ready-state regression passes; the object guard covers other scalar JSON entries as well.

**Fix verdict totals:** 4 CONFIRMED, 4 INCOMPLETE, 0 WRONG, 0 REGRESSION. Incomplete items above retain their cycle-1 identities and are deliberately not re-numbered as new findings.

## Findings (NEW, not in cycle 1)

### [major] F1 — Readable pipe errors escape MCP failure handling and can crash the host

`src/mcp/client.ts:340–349,1556–1562` — The client subscribes to stdout data/end and stderr data, but neither readable has an `error` listener; the spawn's child-process error guard does not handle errors emitted by those separate stream objects. A stdout/stderr read error therefore becomes an unhandled EventEmitter error instead of an in-band transport failure and server-isolated teardown. An inline reproduction against the existing mock emitted `error: simulated read EIO` on each readable: both emissions synchronously threw, whereas stdin has an explicit error handler. A readable destroyed/closed without `end` also has no terminal detector on stdout. **Suggested fix:** install lifetime-safe readable error handlers, fail the server on stdout read failure/unexpected close, choose and document the stderr-error disposition, and absorb late shutdown echoes just as for stdin. Add startup/ready/error-after-close cases; they are absent from the scoped unit tests.

### [minor] F2 — An envelope failure does not stop dispatching the rest of its stdout chunk

`src/mcp/client.ts:1069–1087,1118–1122,1283–1308` — `dispatch()` terminal-fails an invalid envelope but returns only to the enclosing line loop; `onStdout()` continues parsing the remaining lines, and `admit()` has no closed-state guard. Consequently input after the terminal violation can enqueue mandatory replies and restore nonzero reservations on a closed client. Concrete reproduction: one chunk containing `{}\n` followed by a valid server request produces `{undrained:82, queued:1, pending:0}` after failure, rather than zero/inert terminal accounting. Subsequent valid notifications in that chunk also continue changing diagnostics; a large remainder can retain up to the queue cap despite teardown already running. This differs from JSON syntax failure, whose branch returns immediately. **Suggested fix:** return immediately after dispatch if closed (or guard the loop condition), reject admission once closed, and clear retained partial input on teardown. Test a coalesced invalid envelope followed by requests/notifications, not only separate post-close emissions.

### [major] F3 — Busy TUI restart tears down MCP and spawns replacement without draining the active turn

`src/tui/run.tsx:619–631,650–661,872–878` — The busy `/restart` path calls `controller.abort()` and immediately starts `restartTui`, which awaits only MCP teardown before synchronous replacement spawn. There is no promise/barrier for the existing `runPrompt`/`runTurn` to finish. Abort is a signal, not completion: a pending MCP call is settled by teardown, after which the old run still has asynchronous tool-result/session/event work to finish (`runPrompt` continues at `696–708`). If process-group cleanup finishes before that work (for example, while the aborted run is still awaiting a stream completion), `spawnSync` freezes the parent and the replacement replays the same session before the parent has recorded its final result/abort state. The old continuation can then append after the replacement exits. The plain REPL explicitly drains its Telegram turn mutex before MCP teardown, but this TUI path has no analogous drain. **Suggested fix:** retain and await the active TUI turn's completion promise after abort and before MCP teardown/replacement spawn; keep `restartInFlight` set through that barrier. Add a deterministic restart-order test with a deliberately delayed abort completion asserting no teardown/replacement occurs before the old turn's final session write. This finding is established by the scoped control flow; no live TUI/e2e run was performed.

**New finding totals:** 0 blocker, 2 major, 1 minor. These three are independent of the unresolved cycle-1 branches listed above.
