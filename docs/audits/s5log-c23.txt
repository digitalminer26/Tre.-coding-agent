Q1. Throws from assertClaimHeld after the mutation fsync (path-gone, inode-swap, token-mismatch) leave: the data bytes durable and the watermark already advanced (provenThrough/provenOn are set before the ack fence). The claim is released by finally. The ack is withheld, so the caller sees S5LockLostError with the record durable. Because the watermark covers bytes this instance synced, a successor that re-appends the same bytes is classified as refiled via NDR-r, not duplicated; the watermark does not create a false "proven" over bytes that were never synced, since the sync did run on that descriptor. Residual: the caller must treat the outcome as unknown (the header already says so).

Q2. Between the S_IFDIR stat and openSync of the claim, a dir-to-file swap yields ENOTDIR from openSync (not ENOENT/EEXIST), which the claim-open catch rethrows as a raw errno wrap with `.code: "ENOTDIR"`. That matches the stable code but the message is the generic "lock acquire failed", not the legacy-file text. Not in the header taxonomy; a one-sentence addition is warranted. No existing `catch (S5LockBusyError)` swallows it, since it is a plain Error and bypasses that instanceof check.

Q3. releaseLock's rmdirSync is best-effort and only runs on a registry that we created and claimed. The forged legacy file case never reaches acquireLock's success path (it throws ENOTDIR before creating a claim), so no instance of ours can hold a claim under a non-directory registry. Our own claim file is unlinked before rmdir and is never orphaned outside the registry by this path. CLEAN.

Q4. CLEAN for the ENOTDIR guard on the claim fence. Two hardest scenarios I could construct:
- Scenario A: the ack fence passes, then the claim is stolen and the directory is replaced by a file before the `touchLock` call. touchLock swallows errors, so the ack returns while the claim is gone. This is the post-fence window already documented as "HONEST LIMIT"; it is an acknowledged residual, not a new defect.
- Scenario B: the legacy-file guard fires for an entry that is a symlink to a directory. statSync follows the link, so this is accepted as a directory; the claim is then created inside the link target. Operator-visible, documented as out of scope.
