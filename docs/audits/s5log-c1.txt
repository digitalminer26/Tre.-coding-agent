**Q1 (mutual exclusion / watermark):** None found. Two admitted holders would need both to see exactly one entry, which requires one to miss the other's create. Each contender enumerates after its own O_EXCL create, so at least one sees two entries and yields. The watermark only advances after an fsync on the fd whose identity is recorded, and invalidation precedes every mutation.

**Q2 (pre-return identity gate):** Not impossible. The gate compares (dev, ino) only, and the snapshot was classified from an fd that has since been closed. If the original file is unlinked and a new file gets the same inode number (ext4/tmpfs reuse freed inode numbers), the gate passes while the path now holds different bytes. The gate cannot see content changes, and the fold's stated rm+recreate coverage does not hold under inode reuse.

**Q3 (release on error paths):** One gap. In `acquireLock`, when `liveClaims()` returns no entry for our name, the code closes the fd and throws `S5LockLostError` without unlinking our entry. If the entry actually exists (readdir failed transiently, so `liveClaims` returned `[]`), it is left on disk carrying our live pid, which `sweepStaleClaims` will never remove.

**Findings**

1. **MAJOR: replay gate can pass on a reused inode (Q2).**
   Scenario: `readState` opens the file, reads it, and closes the fd (identity X, content A). An external `rm` frees inode X, and an external recreate reuses inode number X with content B. `replay()` then reaches `assertSameInode(state.identity ?? this.provenOn, identityOfPath(path))`, which passes. The snapshot returns content-A records for a file whose bytes are B.
   Wrong outcome: a consumer acts on records no longer standing at the path, with no error raised.
   Region: `replay()`, the pre-return gate; `readState` identity capture.
   Fix direction: bind the gate to a fresh fd read or re-read the bytes and compare, not just the inode number.

2. **MAJOR (liveness): self-wedged registry after a readdir failure (Q3).**
   Scenario: process P creates `claim-<P>-…`, then `liveClaims()`'s `readdirSync` throws (e.g. EMFILE). It returns `[]`, so `mine === undefined`. P closes the fd and throws `S5LockLostError` without unlinking the entry. The entry carries P's pid, and P stays alive, so `sweepStaleClaims` skips it (`pidAlive` true). Every later acquirer, including other processes, sees a live foreign entry and refuses until P exits.
   Wrong outcome: the log becomes unwritable until process exit, even though no holder exists.
   Region: `acquireLock`, the `mine === undefined` branch; `liveClaims` catch returning `[]`.
   Minimal fix: on that branch, also `unlinkSync(claimPath)` best-effort, and make `liveClaims` return an error or mark it unknown rather than an empty set.

3. **MINOR: the mkdir-ENOENT retry has no deadline check.**
   Scenario: if `mkdirSync(regPath)` keeps returning ENOENT while `mkdirDurably` reports nothing to create, the `continue` at that branch skips both the `Date.now() >= deadline` test and the sleep. The loop spins without honouring `lockWaitMs`.
   Wrong outcome: a busy loop that does not refuse at the deadline. This needs a repeatedly vanishing parent, so the impact is limited.
   Region: `acquireLock` step (1), the `code === "ENOENT"` branch.
