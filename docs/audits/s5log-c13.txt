**Q1.** The pass-order list ("acquire → read → (c0) → bootstrap ritual if marker missing → make() → (c1c) → …") matches appendUnit, and the V-g4 carve-out matches the code. Two sentences overstate. "ONE FSYNC PER PASS" says "the pass never re-syncs the dir", but the ritual's `log-dir` and `marker-dir` syncs and the `marker-file` sync do run in a cold pass, so the header's "one fsync" claim is only true for the log fd and must say so. Also the bootstrap is described as running "when the marker is missing or the log is absent", but `ensureEstablished` also re-runs the ritual when the marker is `unreadable` (malformed), and the header's pass-order line does not say that; it is incomplete rather than wrong. The statement "a `make()` refusal after it leaves the re-created marker in place" is accurate.

**Q2.** The c12 test pins: no `append` sync, content byte-identical, `log-file` present, marker present. It does not pin the claim that the ritual runs before `make()` (it only shows `log-file` was called, not the ordering relative to make). A reordering that moved the ritual after make() would still pass if make() did not throw before the ritual. The c10-F1 and c11 tests pin exact sync counts and therefore do pin their claims; they would fail on a regression that added a second decision fsync. Neither covers the unreadable-marker ritual path explicitly in the c12 context.

**Q3.** Concrete defect candidate, traced: `appendUnit` on a warm log with marker deleted, where `make()` returns `[]` and state has `tailKind === "none"`. The early `refiled-only` return skips the bootstrap-only fsyncs' outcome, but that is documented. I found no provable wrong-observable-outcome defect beyond the Q1 wording gaps. Hardest-tried scenarios: (1) rm + recreate between `assertClaimHeld` and the mutation fd open (covered by `assertSameInode` on `state.identity ?? provenOn`); (2) a refiled-only receipt after an in-place same-inode swap (covered by `assertSnapshotIntact` digest gate). Both hold on the code as written.

Findings:
1. (Doc, provable-wrong) The ONE FSYNC PER PASS section says no dir re-sync occurs and implies one fsync per pass; a cold pass on an absent log issues `log-file`, `log-dir`, `lock-acquire`, `marker-file`, `marker-dir`, plus the decision sync. Observable: a reader counting fsyncs per pass from the header gets a wrong count. Fix the wording to "one DECISION fsync; establishment and lock syncs are additional".
2. (Doc, incomplete) The bootstrap carve-out omits the unreadable-marker trigger in `ensureEstablished`, which is the path the c11 test exercises.
3. (Test gap) The c12 test does not assert ritual-before-make ordering, so the header's ordering claim is not falsifiable by it.
