**Findings**

1. **MINOR (false refusal, Q2): transient listing failure refuses without waiting.**
   Scenario: the first `liveClaims(regPath)` call after our `openSync(claimPath, "wx")` hits a transient `readdirSync` error. It returns `listingFailed: true` with an empty list, so `mine === undefined` and `listingFailed` is true. The code unlinks our entry and throws `S5LockBusyError` at once, even though `lockWaitMs` has not elapsed and the registry may be empty. Observable outcome: a busy refusal under a one-off EMFILE, when a retry would have succeeded.
   Region: `acquireLock`, the `mine === undefined` / `listingFailed` branch.
   Fix direction: on `listingFailed`, unlink and fall through to the deadline/backoff path instead of throwing immediately.

2. **MINOR (dead recovery path, Q3): same-instance deletion re-establish always fail-stops.**
   Scenario: a pass's `readState` reads a file (identity X). An external actor deletes the log before the mutation phase. The `!existsSync` branch re-runs `ensureEstablished()`, which creates inode Y. `assertSameInode(state.identity ?? this.provenOn, identityOfFd(fd), …)` then compares X against Y and throws `S5LogIdentityError`. The documented recovery never completes, and the caller sees a refusal after it has already recreated the file and republished the marker.
   Region: `appendUnit`, the post-`assertClaimHeld` `!existsSync` branch and the mutation-descriptor identity check.
   Fix direction: after re-establishment, rebind the expected identity to `provenOn` (the newly established inode), or refuse before re-establishing so the file is not recreated on a failing pass.
