## Findings

1. **HIGH — Ordered marker rejected by CommonMark still opens comment state**

   Appended after the valid base document:

   ```markdown
   paragraph
   2. <!--

      §99999
      -->
   ```

   **Expected:** Both commonmark.js and markdown-it render `2. <!--` as paragraph text: an ordered list starting at 2 cannot interrupt a paragraph. The blank line ends that paragraph, and `§99999` is visible in a subsequent paragraph.

   **Actual:**

   ```text
   $ node scripts/contract-check.mjs docs/audits/probes-r21-c1/ordlaunder.md
   exit 0
   stderr: empty
   ```

   The checker launders the visible ref. `trackList` correctly refuses the interrupting marker, but `atBlockStart` independently accepts the same marker as a container prefix.

   **Minimal fix:** Make `atBlockStart` use the actual accepted container context, including the paragraph-interruption rule, rather than recognizing list-marker syntax independently. Fail closed if container recognition is uncertain.

2. **LOW — Inline code span ref is reported despite the requested span-masking contract**

   ```markdown
   hello `§99999` world
   ```

   **Expected:** Under the requested C9 rule that code spans are masked, the ref is inside a code span and should not be reported. Both reference parsers render it as `<code>§99999</code>`.

   **Actual:**

   ```text
   $ node scripts/contract-check.mjs docs/audits/probes-r21-c1/spanmasked.md
   exit 1
   stderr: ... FAIL C9 ... line 6003: §99999
   ```

   The checker intentionally copies closed span contents into the scanned output.

   **Minimal fix:** Mask closed code-span contents in the C9 input while preserving offsets; apply the same policy to correctly paired multiline spans. This differs from the checker’s current documented policy that span text is normative.
