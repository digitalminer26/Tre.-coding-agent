===== CONTINUATION (findings+verdict) =====

F1 [CONFIRMED-WRONG] `ensure()` crash-recovery re-attach uses unqualified `worktree add <path> <branch>` — a same-named tag shadows the branch (git ref-rev-parse order puts refs/tags/ before refs/heads/), so the worktree is created DETACHED at the tag's commit; the post-creation `head !== baseSha` check passes when the tag is at base, so `ensure` returns `branch:"agent/ep/t"` for a detached worktree (false provenance). Repro: `git tag agent/ep4/t1 <base>; git branch agent/ep4/t1 <base>; git worktree add /tmp/w agent/ep4/t1` → `git -C /tmp/w rev-parse --abbrev-ref HEAD` = `HEAD` (detached), not the branch. Fix: `worktree add <path> refs/heads/<branch>`.

F2 [CONFIRMED-WRONG] `remove()` doc comment still says "`worktree remove` (--force only when forced)" and the class "Conservative rules" block never mentions `locked`; the code now passes `-f -f` for locked and throws `locked` from `prune()`. Doc drift on the error contract (docs/11 not attached — unverified there). Repro: read the `removeTaskWorktree` doc comment vs the `forceArgs` line.

F3 [RISK] No test covers locked+DIRTY force removal (the 4th combo). The `-f -f` path is only tested on a clean locked worktree; a dirty locked worktree relies on `-f -f` also overriding the dirty gate inside git (it does, but untested). Repro: lock a worktree, write an untracked file, `removeTaskWorktree({force:true})` — no test asserts this.

F4 [RISK] `users` pre-gate in `remove()` includes locked+vanished registrations (it does not filter `entryGone`), so a stale locked entry on the same branch yields `branch-in-use` instead of the actionable `stale-registration`/`locked` guidance. Repro: lock wt A, `rm -rf` A, then `removeTaskWorktree` for a second worktree on the same branch with `deleteBranch:true` → `branch-in-use`.

F5 [RISK] `entryGone` treats a locked entry whose path exists but is a FILE (or an empty dir) as live (`dirExists` is `stat().isDirectory()`); `ensure` then returns `preexisting:true` and the caller writes into a non-worktree. Repro: lock wt, `rm -rf` dir, `touch <path>` → `ensure` returns preexisting.

F6 [RISK] `prune()`'s `lockedStale` gate throws `locked` for ANY locked stale entry under wtRoot, including one that is also foreign-adjacent; combined with the foreign-first order, a locked foreign stale entry is permanently unprunable by this wrapper (F9 design, but now the operator gets `prune-refused` with no path to `locked`). Repro: foreign locked vanished wt → `prune()` → `prune-refused`.

F7 [RISK] `branch -D <entry.branch>` is unqualified; a branch literally named `-foo` (creatable via `git branch -- -foo`) makes `git branch -D -foo` parse `-foo` as an option → git-failed AFTER `worktree remove` already succeeded (partial mutation). Repro: `git branch -- -foo; git worktree add /tmp/w -foo` then remove with deleteBranch.

F8 [NOT-A-DEFECT] `entryGone` unlocked-vanished path: git marks unlocked vanished entries `prunable` synchronously in `worktree list --porcelain` (lstat at list time, no `--expensive-scan`/`pruneExpiry` gate for the unlocked case); verified by the existing `ensure: vanished worktree directory → stale-registration` test passing without the locked branch.

F10 [NOT-A-DEFECT] `-f -f` for locked, `--force` for dirty-unlocked: all four combos resolve correctly (clean/unlocked plain; dirty/unlocked `--force`; clean/locked `-f -f`; dirty/locked `-f -f` — git's double force overrides both gates in one shot).
