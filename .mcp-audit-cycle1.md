## Findings

### [major] F1 — Stdout decoding corrupts UTF-8 characters split across pipe chunks

`src/mcp/client.ts:953–955` — Each incoming Buffer is independently decoded with `chunk.toString("utf8")`. A pipe can divide a multibyte character at any byte, so a completely valid MCP JSON line can be silently corrupted before parsing. Reproduction: return the text `你好🙂` and split the stdout Buffer after the first byte of `你`; `callTool()` succeeds but returns `���好🙂`. This also changes the byte count used by the subsequent frame-limit checks, potentially rejecting a valid near-limit frame. The mock normally writes whole JSON lines, so existing tests miss this. **Suggested fix:** frame raw bytes and decode complete lines, or use a persistent UTF-8 `StringDecoder` with independent raw-byte frame accounting. Add tests splitting CJK and emoji at every byte boundary, including a near-limit frame.

### [major] F2 — Timed-out unsent requests remain queued and execute after the caller sees failure

`src/mcp/client.ts:645–647,1303–1314` — The timeout callback calls `settle()`, but settlement never removes/releases `p.frame` when its write has not started. Only explicit abort does that (`879–896`). Thus a request waiting behind a stalled active write times out locally but remains queued; when the pipe recovers it is sent to the server, potentially performing a mutation after the agent has already reported failure or retried it. It also retains queue capacity and can contribute to a later stall failure despite having no pending caller. Reproduced with two small requests and a 25 ms timeout: after both expired, stats were `{ undrained: 550, queued: 1, pending: 0 }`; resuming writes transmitted the second, expired request. **Suggested fix:** make ordinary settlement remove/release an unsent frame exactly once, while preserving write-started reservations until flush; include probe-timeout settlement where applicable. Test queued timeout removal, restored admission capacity, and absence of any later transmission.

### [major] F3 — Negotiation accepts arbitrary unsupported versions and invalid discovery results

`src/mcp/client.ts:390–419,482–493,516–522,536–547` — Version selection uses the server's first advertised value rather than an intersection with explicitly client-supported versions; legacy initialization accepts any string version without checking or recording it. Discovery validation checks only that `resultType` is some string and `supportedVersions` is an array, and a successful retry is not checked to ensure it actually supports the selected version. Consequently the client can become ready while claiming a protocol it does not implement, contrary to the documented unknown-version/startup-failure contract (§6). Reproductions accepted legacy `protocolVersion: "alien-version"`; a modern `-32022` advertising only `"alien-version"`, followed by `{ resultType: "garbage", supportedVersions: [123] }`, also reached ready and sent later `_meta.protocolVersion: "alien-version"`. **Suggested fix:** define supported versions per era, choose only their intersection, validate discovery discriminant and string-array entries, verify retry agreement, and validate/cache the legacy negotiated version. Reject incompatible/invalid startup results and tear down that server. Add negative tests; the current retry test only checks a server-chosen version and does not establish mutual support.

### [major] F4 — Server tool annotations are discarded before safety classification

`src/mcp/client.ts:586–590`; `src/mcp/registry.ts:194–196`; `src/mcp/adapter.ts:402–404` — Pagination reconstructs each tool with only name, description, and schema, losing its per-tool `annotations`. The registry supplies only `trusted`, while the adapter reads a single optional import-level `opts.annotations` instead of each tool's annotations. Thus real imported tools never carry `mcpAnnotations`, even when the server reports `readOnlyHint: true`. This violates the documented safety matrix: read-only MCP tools are unnecessarily prompted, and are blocked in no-prompt mode instead of allowed; destructive metadata is also unavailable. An end-to-end mock registry reproduction supplied a read-only annotation and observed `result.tools[0].mcpAnnotations === undefined`. **Suggested fix:** preserve annotations in `McpTool`/pagination and forward each individual tool's annotations when adapting it. Add registry-to-adapter coverage with differently annotated tools, rather than testing metadata only on manually constructed tools.

### [minor] F5 — Ready-state terminal failures do not complete registry resource cleanup

`src/mcp/registry.ts:267–278`; `src/mcp/client.ts:1358–1364` — The transport's terminal-failure action calls only `spawn.kill()`. Unlike startup failures, there is no subsequent registry close/confirmation/dispose path when a previously ready client fails. Sandbox policy directories/empty roots and the `liveSpawns` entry remain owned until the user eventually quits or restarts, contrary to §4.4's full teardown on ready-state terminal failure. A registry reproduction triggered stdout EOF after ready and observed one kill but zero close/dispose calls; those ran only after explicit `teardownAll()`. **Suggested fix:** add an idempotent asynchronous terminal-failure cleanup hook that confirms group termination before unregistering/disposal, retains the backstop on unconfirmed termination, and catches/reports cleanup errors. Test post-ready EOF, write failure, and framing failure with disposal counters.

### [minor] F6 — Rejected tool frames leak request-scoped abort listeners

`src/mcp/client.ts:659–662,670–679` — Tool admission failure directly deletes the pending entry and clears its timer instead of using settlement, so `p.cleanupAbort` is never called. A rejected oversized/queue-full request leaves its abort closure attached to the caller's signal; client teardown cannot find it afterward because the pending entry is already gone. Repeated rejected calls sharing a turn signal accumulate listeners and retain the client until that signal is released/aborted. Instrumented reproduction observed one listener registration, zero removals after rejection, and still zero removals after `close()`. **Suggested fix:** route admission rejection through the common settlement helper (including cleanup), or explicitly detach the listener before deleting the entry. Add repeated admission-rejection coverage using one signal.

### [minor] F7 — The advertised 64 KiB stderr ring is still capped in characters, not bytes

`src/mcp/client.ts:983–987` — The stderr tail uses JavaScript string length/slicing against `MCP_STDERR_RING`, although the constant and scope define a 64 KiB bound. A reproduction writing 65,536 CJK characters retained 196,608 UTF-8 bytes. It also uses independent chunk decoding, with the same split-character problem as stdout. This is separate from the correctly fixed resource-output cap. **Suggested fix:** retain a byte-bounded Buffer tail (decode safely when exposing diagnostics), or maintain a streaming decoder and a UTF-8-byte-bounded text tail without splitting code points. Add multibyte stderr tests rather than only the current ASCII test at `test/mcp-client.test.ts:731`.

### [minor] F8 — Null tools/list entries escape the intended in-band error taxonomy

`src/mcp/client.ts:580–584` — `entry.name` is accessed before `isObj(t)` validates the entry. A valid JSON-RPC result containing `tools: [null]` therefore throws a raw `TypeError` instead of `McpCallError` in ready-state `listTools()`. Reproduced after successful startup: `TypeError: Cannot read properties of null (reading 'name')`. Startup happens to catch and tear down the server, but the shared ready-state API violates its documented result-payload failure contract. **Suggested fix:** validate `isObj(t)` before dereferencing any field and use the existing startup/call-specific error helper. Add null/scalar entries to startup and ready-state list validation tests.
